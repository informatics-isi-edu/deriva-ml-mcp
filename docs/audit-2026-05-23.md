## Headline findings

1. **Three HARD stateless violations** in the existing tool surface,
   all clustered in the execution-staging lifecycle. The plugin
   inherits per-server SQLite manifest state from deriva-ml's
   `Execution._manifest_store`, which fundamentally breaks the
   multi-tenant MCP server model. The two tools — `add_feature_values`
   and `commit_execution` — work only when the server is also the
   machine that staged the work; in any other deployment, the
   server's manifest is empty and the user's local manifest is
   invisible to the server.

2. **Plugin is keeping up with deriva-ml.** v1.37.2..v1.38.0 is
   mostly internal P1 refactors. The few user-visible changes
   (write-through description setters, typed `DerivaMLRidsNotFound`
   exception, `Asset_Role` contract, `Output_File`/`Input_File`
   auto-tags) are minor uplifts, not breaking changes. The plugin's
   response-model contracts, tool registrations, and resource URIs
   are all still aligned with v1.38.0.

3. **Skills lag behind the MCP surface by ~50%.** Four tools added
   since the 2026-05-13 e2e audit (`bootstrap_config`,
   `validate_config_file`, `create_vocabulary`, `workflow_type`
   filter) plus two new resources (`bag-preview`,
   `deriva://deriva-ml/{getting-started,concepts}`) are documented in
   at most one skill each — most call sites that would benefit have
   not been updated. This is a `deriva-ml-skills` problem, not a
   plugin problem, but it constrains real-world leverage.

4. **One documented-but-hallucinated parameter in `manage-storage`
   skill.** `cache_dataset(asset_rid=...)` doesn't exist; the tool
   only accepts `dataset_rid`. Asset download is correctly
   Python-only per the stateless rule.

## Section 1 — Stateless / bounded-resource rule (Lens C)

### 1.1 The rule

> **MCP operations must be stateless on the server side and consume
> bounded resources per call.** Operations that require significant
> data localization, server-side persistent storage, or managed state
> (per-user SQLite registries, `~/.deriva-ml/` caches, local git
> checkout dependencies, materializing unbounded data) must NOT be
> exposed as MCP tools or resources. They belong in skill-driven
> Python that the user runs locally.

### 1.2 Posture today

**3 HARD / 2 SOFT / 2 GRAY violations out of 62 total surface items
(45 tools + 17 resources).** The surface is clean overall; the
violations cluster in one cohesive area (the staged-execution
lifecycle) plus two narrow fixes.

### 1.3 HARD violations (need real action)

| # | Tool | Evidence | Recommendation |
|---|------|----------|----------------|
| 1a | `deriva_ml_commit_execution` | `tools/execution/mutate.py:503-518` reads from `execution._manifest_store` (per-execution local SQLite) and uploads from server-local staging dir | **Deprecate from MCP surface.** Move to a `work-with-executions` skill that generates user-local Python (same pattern as the existing `work-with-assets` skill in `deriva-skills`). |
| 1b | `deriva_ml_add_feature_values` | `tools/feature.py:759-775` calls `execution.add_features(records)` which appends to the per-execution local manifest store; pairs only with the same server's `commit_execution` | **Deprecate from MCP surface.** Same skill-based replacement as 1a. Alternative: rework upstream `add_features` to write catalog rows directly (no staging) when called through MCP — but the upstream change is non-trivial. |
| 1c | `deriva_ml_validate_config_file` — `file_path=` branch | `tools/dataset/read.py:1101-1104` reads `file_path` from the server's filesystem; docstring at line 1032-1036 already acknowledges this. The `file_contents=` branch is fine. | **Drop the `file_path` parameter.** Require `file_contents`. One-line API surface trim. |

The HARD violations 1a + 1b are the architecturally important ones.
Their existence pre-dates the formalized rule; they appear correct
only because in single-machine development (the deriva-docker
localhost deployment) the MCP server IS the user's machine. A
multi-tenant deployment (the eventual target) would expose the
breakage immediately.

The recommended fix mirrors the `work-with-assets` skill in
`deriva-skills/` — file I/O lives outside the MCP surface;
the skill teaches the LLM to write Python the user runs
locally. The same model applies to the staged-execution lifecycle:
`create_execution` → `start_execution` → `add_features` (locally) →
`commit_execution` (locally) → catalog row visibility. The
catalog-row-create operations (`create_execution`, `start_execution`,
`abort_execution`) stay on MCP because they are pure catalog state
changes; the staged-work operations move out.

### 1.4 SOFT violations (defensible to defer)

| # | Item | Issue | Recommendation |
|---|------|-------|----------------|
| 2a | `deriva://catalog/{h}/{c}/ml/dataset/{rid}/bag-preview` resource | `resources/ml.py:472-473` (via `_bag_info_impl`) returns `cache_status`/`cache_path` that describe the **MCP server's** cache, not the user's | Drop `cache_status` / `cache_path` from the resource payload. The row-count and byte-total fields are stateless and stay. |
| 2b | `deriva_ml_denormalize_dataset` (rows branch) | `tools/dataset/complex.py:320-333` materializes up to `_MAX_LIMIT+1` rows server-side; 10× preflight guard at line 285-304 is correct. Bounded today. | Keep. Worth a watch-flag: if upstream `get_denormalized_as_dict` ever loses its streaming behavior (currently documented at line 191-192), this becomes a HARD violation overnight. |

### 1.5 GRAY (design discussion)

| # | Item | Issue | Status |
|---|------|-------|--------|
| 3a | `deriva_ml_create_execution` | Creates a catalog row (stateless, fine) **plus** initializes a per-execution working dir + manifest store on the server. | **RESOLVED** — v0.5.0 removed the tool entirely (commit `2730a6f`). |
| 3b | `deriva_ml_cache_dataset` | Known HARD violation (materializes to MCP server disk). | **REOPENED** as `docs/superpowers/notes/2026-05-23-cache-denormalize-deprecation-design.md`. Three options on the table; pending decision. |

### 1.6 Tools that PASS audit (good models)

- **`deriva_ml_list_*` family** — cursor-paginated, `_MAX_LIMIT`-bounded,
  no server state. Canonical example: `_list_datasets_impl` in
  `tools/dataset/read.py`.
- **`deriva_ml_validate_dataset_specs` / `validate_execution_configuration`**
  — pure metadata round-trips, bounded by config size, no filesystem.
  `tools/dataset/read.py:861-1010`.
- **`deriva_ml_list_feature_values`** — `tools/feature.py:413-453` caps
  via the v3.1 `max_results` parameter; propagates
  `DerivaMLMaterializeLimitExceeded` cleanly. Textbook bounded-resource
  pattern.
- **Asset module** — `tools/asset.py:14-20` has an explicit module
  docstring carve-out: "file I/O lives in a skill, not the MCP surface."
  This is the template for the recommended deprecation of 1a/1b.

## Section 2 — deriva-ml v1.37.2 → v1.38.0 surface changes (Lens A)

### 2.1 No genuinely new stateless surface

Most of the audit range (~25 of 30 commits) is internal P1 audit
refactors — extracting helpers from god-classes without changing
public APIs. The previously-discussed `validate_config_file` /
`bootstrap_config` (#192) are **already wrapped** as
`deriva_ml_validate_config_file` and `deriva_ml_bootstrap_config`.

### 2.2 New APIs deliberately NOT wrapped (state-bound)

| API | Reason |
|-----|--------|
| `split_dataset(ml, source_rid, execution, ...)` (#191) | Requires live `Execution` context manager; writes `split_config.json` to `exe.working_dir`. **Python-only by design.** Already retired from MCP surface (commit `9fe47f6`). |
| `Asset.download(dest_dir)` (#214 fix) | Writes bytes to local Path. **Python-only.** |
| `localize_assets` cross-host (#193) | Moves Hatrac bytes, rewrites catalog URLs in bulk. Operator-only with rehearsal mode. **Python-only.** |

### 2.3 Existing MCP wrappers that may need updates

**C1 — `update_dataset` / `update_asset` simplification (#221).**
deriva-ml v1.38.0 introduced write-through `@property/@setter` on
`Asset.description` and `Dataset.description`. The plugin currently
routes description writes through a `_set_row_description` helper
added precisely because deriva-ml didn't expose write-through setters.
That helper and its `_write_asset_description` cousin can both be
removed; the setters perform the catalog write directly.

- Files: `_helpers.py:250-287`, `tools/dataset/mutate.py:557-570`,
  `tools/asset.py:210-229`.
- Tidiness win, not a correctness fix. Bump `deriva-ml>=1.38.0` pin.
- Also drop stale docstring claims at `tools/dataset/mutate.py:474-478`
  and `tools/asset.py:430-432` saying "deriva-ml doesn't expose a
  catalog-write setter for description."

**C2 — `DerivaMLRidsNotFound` typed exception (#196).** Carries
structured `missing_rids: set[str]`. Currently flattened by
`_error_envelope` into a generic string. Tools that take RID lists
(`add_dataset_members`, `delete_dataset_members`, dataset/asset_types
update branches) could surface this as `{"error": ..., "missing_rids":
[...]}` — same pattern as the existing `NoAssociationException`
handling at `tools/asset.py:181-185`. Bump `deriva-ml>=1.37.6`.
**Low priority** — current error envelope works; this is a richer
diagnostic.

**C3 — `Output_File` / `Input_File` auto-tagging (#220).** deriva-ml
now auto-adds directional `Output_File`/`Input_File` tags to every
execution-linked asset's `asset_types`. The plugin's `list_assets` /
`lookup_asset` tools surface `asset_types` verbatim — an LLM that
filters `asset_types == ["Model_File"]` will start seeing zero results
post-upgrade. **Add a one-sentence note** to the two tools'
docstrings explaining the directional tags are auto-managed.

**C4 — `Execution_Execution` exclusion (#220).** Silent win. The
plugin's `_get_execution_detail_impl` calls
`record.list_assets(asset_role="Input"/"Output")`; pre-v1.38.0 this
crashed on any execution participating in nested-execution chains.
The fix is transparent — no code change needed; worth one comment
update at `tools/execution/read.py:254-257`.

### 2.4 New conceptual content for prompts

**D1 — Asset_Role contract.** PR #220 + the deriva-ml CLAUDE.md
refresh (#223) pinned the contract: every execution-linked asset
carries both `Asset_Role` (`Input`/`Output`) and a directional
`Asset_Type` tag (`Input_File`/`Output_File`); deriva-ml assigns
both, never the caller. The plugin's `_CONCEPTS_GUIDE` (in
`src/deriva_ml_mcp/prompts.py`, around the `Asset` definition at
lines 169-178) says nothing about this. **Add a one-paragraph
Asset_Role contract block** to `_CONCEPTS_GUIDE`.

Per the cross-repo sync rule in `prompts.py`'s preamble, the
analogous content must also land in `deriva-ml-skills`'
`deriva-ml-context/SKILL.md`. Defer until the next time
`_CONCEPTS_GUIDE` is touched for another reason (so the dual-edit
is amortized), unless the LLM filter-surprise from C3 makes it
urgent — in which case D1 + C3 land together.

**D2 — `CatalogState` state-machine refresh.** PR #223 renamed the
deriva-ml test infrastructure state-machine names. Library-internal;
no MCP prompt impact. The user-facing lifecycle state machine on
`Execution_Status` (`Created` → `Running` → `Completed` / `Failed`
/ `Aborted`) is unchanged.

### 2.5 Overall posture vs deriva-ml

**No drift.** Plugin keeps pace with v1.38.0 on all contracts.
Priority order if acting: C1 (simplification + bump pin) → D1
(Asset_Role prompt content) → C3 (asset_types docstring note) → C2
(richer error envelopes; do when convenient).
